## Purpose

This file is the source of truth for Backup Manager implementation progress. Update it whenever a task starts, finishes, changes scope, is blocked, or produces an important decision.

Backup Manager protects servers, files, databases, and infrastructure workloads. It is separate from the existing Settings > Backup & Restore screen, which protects DeployerX account and workspace data.

## Status Legend

- `[ ]` Planned
- `[~]` In progress
- `[x]` Completed and verified
- `[!]` Blocked; the progress log must explain why

## Working Rules

1. Move only one primary implementation task to `[~]` at a time unless work is explicitly parallelized.
2. A task becomes `[x]` only after its acceptance criteria have been verified.
3. Record changed files and verification evidence in the progress log.
4. Add newly discovered work to the appropriate phase instead of keeping it only in chat history.
5. Database backups must use database-aware consistency mechanisms; copying live database files is not an acceptable generic implementation.
6. Synchronization and mirroring must not be presented as versioned backup.

## Product Decisions

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-08-03 | Backup Manager is a separate application module. | Infrastructure backup and DeployerX account export are different products and recovery domains. |
| 2026-08-03 | A persistent worker will own scheduled execution. | Desktop UI availability cannot determine whether scheduled protection runs. |
| 2026-08-03 | File repositories will use a proven engine behind an adapter. | Repository formats, deduplication, encryption, pruning, and verification are high-risk to implement from scratch. |
| 2026-08-03 | Database adapters will use database-native consistency mechanisms. | Generic copying of live database files can produce unrecoverable backups. |
| 2026-08-04 | Engine tasks may finish at a tested provider/controller contract when concrete infrastructure is owned by a later platform task. | Registering an in-memory or no-op backend in production would advertise protection that the worker cannot safely provide; MongoDB LVM/ZFS/Btrfs and cloud volume execution belongs to BM-502/BM-508, sharded deployment integrations to BM-510, and the cross-adapter drill platform to BM-604. |
| 2026-08-05 | Limit active database delivery to MySQL, MariaDB, PostgreSQL/Supabase, SQLite, MongoDB, Redis, and ClickHouse. | Shipping the workflows used by the broadest customer base is more valuable than extending rare database families; existing out-of-scope work remains isolated for compatibility and recovery safety. |
