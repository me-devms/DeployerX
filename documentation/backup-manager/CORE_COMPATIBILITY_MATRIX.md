# Backup Manager Core Compatibility Matrix

Delivery status and release evidence are tracked in [the core delivery task list](./CORE_TASKS.md).

This matrix is the public compatibility boundary for the core Backup Manager release. A capability is supported only inside the complete version, deployment, scope, restore, privilege, and repository envelope stated below; discovery outside that envelope must fail closed rather than silently downgrade the result.

Engines not listed in this matrix are outside the Backup Manager core scope.

## Repository Names

**All core repositories** means the encrypted and authenticated DeployerX repository engine backed by any of:

- Local folder (`deployerx.repository.local`)
- SFTP server (`deployerx.repository.sftp`)
- S3-compatible object storage (`deployerx.repository.s3-compatible`)

Plain FTP is not a core repository; use SFTP for a remote filesystem destination.

Repository support describes where DeployerX artifacts are retained. It does not expand an engine's native execution or restore compatibility.

## Compatibility Interpretation

- **Full** means a self-contained anchor at the admitted Source scope; it does not mean every resource owned by a managed platform or application.
- **Incremental** means a retained child depends on an authenticated ancestor chain. It implies PITR only where the engine row explicitly says so.
- **Original**, **alternate**, and **new** are adapter-specific restore modes. A mode is unavailable unless its row explicitly includes it.
- Native version, identity, topology, tool, privilege, and destination checks are repeated at execution time. Passing connection discovery alone does not guarantee that a later backup or restore is admissible.
- Every restore authenticates repository metadata and content before success, but application-specific semantic validation remains operator-owned unless an engine runbook explicitly defines it.
