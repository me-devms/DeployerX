# Backup Manager Repository Format

## Status

- Engine ID: `deployerx.repository-engine.files`
- Engine version: `1.0.0`
- Repository format version: `1`
- Compatibility: readers must reject unknown format versions; repository formats are not migrated with `control.db`.

## Responsibility Boundary

The repository engine owns chunking, client-side encryption, keyed content identity, deduplication, manifests, and read verification. Repository adapters own object transport, commits, aborts, capacity, locking, immutability, and destination authentication.

The engine calls only opaque object operations. Adapters never receive plaintext file content, file paths, file metadata, or repository master keys.

## Object Layout

| Object | Key |
| --- | --- |
| Format marker | `repository/format.json` |
| Encrypted chunk | `chunks/v1/{first-two-id-characters}/{64-character-keyed-id}.dxb` |
| Encrypted snapshot manifest | `manifests/v1/{snapshot-id}.dxb` |

Object keys are generated by the engine, use a fixed grammar, and contain no source names or paths.

The format marker contains only the repository ID, engine ID, format version, minimum engine version, and creation time. It contains no workload or secret data.

## Key Derivation and Content Identity

The engine accepts binary master-key material resolved for one execution and never persists it. HKDF-SHA-256 derives separate repository-scoped keys for:

- chunk encryption;
- manifest encryption;
- content identity;
- deterministic snapshot retry identity.

Chunk IDs are HMAC-SHA-256 values over plaintext chunks. They permit deduplication without exposing an ordinary plaintext content hash. Deduplication is scoped to the repository and encryption-key version; key rotation intentionally creates a new deduplication domain.

## Encryption Envelope

Chunks and manifests use AES-256-GCM with a fresh 96-bit random nonce for each newly committed object. The authenticated envelope contains:

1. the eight-byte `DXBKR001` magic value;
2. one object-kind byte;
3. a two-byte key-version length;
4. the 12-byte nonce;
5. the 16-byte authentication tag;
6. the UTF-8 key version;
7. ciphertext.

The magic, object kind, and key version are authenticated as additional data. A wrong key, modified header, modified tag, or modified ciphertext fails closed.

## Snapshot Commit

1. Validate the repository format marker.
2. Derive a deterministic snapshot ID from the run-scoped idempotency key.
3. Split regular-file streams into bounded fixed-size chunks.
4. Derive each keyed chunk ID.
5. Verify and reuse an existing chunk, or encrypt and commit a missing chunk.
6. Build a canonical manifest containing paths, file metadata, ordered chunk references, parent snapshot ID, engine/format versions, and totals.
7. Encrypt and commit the manifest last.

A recovery point must not be cataloged until step 7 succeeds. Interrupted writes may leave unreferenced chunks, but never an advertised partial snapshot. Later pruning may remove unreferenced chunks under the repository lock.

Retrying an already committed idempotency key reads and authenticates the existing manifest and returns the same snapshot rather than creating another version.

## Read and Restore Verification

Manifest reads are bounded, authenticated, parsed, and checked for supported versions, expected snapshot identity, unique paths, bounded file/chunk counts, canonical chunk keys, key-version consistency, and size totals.

Every restored chunk is authenticated, decrypted, recomputed against its keyed content ID, and checked against its declared size. The complete file is checked against its manifest HMAC before restore completion is reported.

Callers must use streaming restore for large files. Materializing a complete file in memory is limited to 256 MiB.

## Initial Limits

| Limit | Value |
| --- | ---: |
| Default chunk size | 4 MiB |
| Chunk-size range | 64 KiB to 64 MiB |
| Files per snapshot | 100,000 |
| Chunk references per snapshot | 1,000,000 |
| Encrypted manifest plaintext | 64 MiB |
| Materialized restore helper | 256 MiB |

These are validation and memory-safety limits, not repository capacity limits. Future format versions may introduce content-defined chunking or compression without changing transport adapters.
